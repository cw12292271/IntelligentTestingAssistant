# 接口测试指南（完整版 V2.0）

## 第一章 接口测试基础

### 1.1 接口测试定义

接口测试是验证系统组件间数据交互的正确性。它介于单元测试和 UI 测试之间，关注的是系统对外暴露的 API 是否按约定工作。

接口测试的核心价值：比 UI 测试更早发现问题、更稳定、更快、覆盖更全。一个接口的测试用例，往往能覆盖多个 UI 场景。

### 1.2 接口测试关注点

请求参数校验：必填参数缺失、参数类型错误、参数超长、参数含特殊字符。

响应状态码：是否符合 REST 规范。

响应数据结构：字段是否齐全、类型是否正确、是否有多余字段。

业务逻辑正确性：正常流程、边界流程、异常流程。

异常处理：依赖服务不可用、超时、返回异常数据。

性能：响应时间、并发能力。

安全性：鉴权、权限、SQL 注入、XSS。

### 1.3 接口测试用例结构

一个完整的接口测试用例应包含：

用例编号、用例标题、优先级。

接口地址、请求方法。

请求头：Content-Type、Authorization、自定义头。

请求参数：路径参数、查询参数、请求体。

预期状态码。

预期响应体：字段校验、值校验。

前置条件、后置清理。

## 第二章 HTTP 状态码规范

### 2.1 2xx 成功

200 OK：请求成功，返回业务数据。

201 Created：资源创建成功，响应头包含 Location。

204 No Content：请求成功，无响应体，常用于 DELETE。

### 2.2 4xx 客户端错误

400 Bad Request：请求参数错误，需检查参数格式和必填项。响应体应包含具体错误字段和原因。

401 Unauthorized：未授权，Token 缺失或失效。响应头应包含 WWW-Authenticate。

403 Forbidden：无权限，Token 有效但无访问权限。例如普通用户访问管理员接口。

404 Not Found：资源不存在。

405 Method Not Allowed：请求方法不支持。

409 Conflict：资源冲突，例如重复创建。

422 Unprocessable Entity：请求格式正确但语义错误，例如参数校验失败。

429 Too Many Requests：请求过于频繁，触发限流。

### 2.3 5xx 服务端错误

500 Internal Server Error：服务器内部错误，需查看服务端日志。

502 Bad Gateway：网关错误，上游服务不可用。

503 Service Unavailable：服务不可用，通常因过载或维护。

504 Gateway Timeout：网关超时，上游服务响应慢。

## 第三章 常见测试场景

### 3.1 参数校验测试

必填参数缺失：逐个删除必填参数，验证返回 400 且提示明确。

参数类型错误：例如 int 类型传字符串、日期格式错误。

参数超长：超出数据库字段长度限制，验证是否被截断或报错。

参数含特殊字符：SQL 注入字符、XSS 字符、Unicode 字符。

参数边界值：数值参数取最小值、最大值、最小值减一、最大值加一。

### 3.2 业务逻辑测试

正常业务流：完整走一遍主流程，验证数据正确。

重复提交：同一请求提交两次，验证幂等性。

并发请求：多个请求同时到达，验证数据一致性。

状态回滚：操作失败后数据是否回滚。

事务一致性：跨表操作时，一张表失败另一张表是否回滚。

### 3.3 异常测试

依赖服务不可用：mock 依赖服务返回 500，验证主服务是否优雅降级。

依赖服务超时：mock 依赖服务延迟响应，验证主服务超时处理。

依赖服务返回异常数据：mock 依赖服务返回格式错误的数据，验证主服务是否能容错。

网络中断：断开网络，验证请求失败时的错误提示。

## 第四章 接口测试示例

### 4.1 登录接口

接口：POST /api/login

请求头：Content-Type: application/json

请求体：
{
  "username": "test_user",
  "password": "123456"
}

正常场景 1：
请求参数正确，预期返回 200，响应体包含 token 字段、用户信息。token 有效期应为 2 小时。

正常场景 2：
用户名含大小写，预期登录成功（用户名不区分大小写）。

异常场景 1：
username 缺失，预期返回 400，响应体提示「用户名不能为空」。

异常场景 2：
password 错误，预期返回 401，响应体提示「用户名或密码错误」。

异常场景 3：
连续 5 次密码错误，预期返回 403，响应体提示「账号已锁定，请 30 分钟后重试」。

异常场景 4：
username 含 SQL 注入字符，预期返回 400，响应体提示「用户名格式错误」。

### 4.2 订单查询接口

接口：GET /api/orders/{order_id}

请求头：Authorization: Bearer {token}

正常场景：
查询自己名下的订单，预期返回 200，响应体包含订单详情。

异常场景 1：
查询他人订单，预期返回 403，提示「无权访问」。

异常场景 2：
order_id 不存在，预期返回 404，提示「订单不存在」。

异常场景 3：
Token 过期，预期返回 401，提示「登录已失效」。

### 4.3 支付接口

接口：POST /api/pay

请求体：
{
  "order_id": "12345",
  "amount": 99.00,
  "pay_method": "alipay"

异常场景 1：
amount 与订单金额不一致，预期返回 400，提示「支付金额错误」。

异常场景 2：
订单已支付，重复支付，预期返回 409，提示「订单已支付」。

异常场景 3：
支付渠道不可用，预期返回 503，提示「支付渠道暂时不可用」。

异常场景 1：

异常场景 2：
密码强度不足，预期返回 400，提示「密码需包含大小写字母和数字」。

异常场景 3：
手机号格式错误，预期返回 400，提示「手机号格式错误」。

异常场景 4：
邮箱格式错误，预期返回 400，提示「邮箱格式错误」。

### 4.5 商品列表接口

## 第五章 接口自动化测试

### 5.1 自动化测试原则

优先覆盖核心业务接口，再逐步扩展到边缘接口。

测试数据与测试代码分离，便于维护和复用。

使用断言库校验响应，包括状态码、字段类型、字段值、响应时间。

每次接口变更后，必须回归相关用例。

### 5.2 自动化测试框架

推荐使用 Pytest + Requests。

Pytest 提供 fixture、参数化、断言等能力，适合接口测试。

Requests 提供简洁的 HTTP 客户端，支持 session、超时、重试。

示例代码：

import pytest
import requests

@pytest.fixture
def base_url():
    return "http://localhost:8000"

def test_login_success(base_url):
    resp = requests.post(
        f"{base_url}/api/login",
        json={"username": "test", "password": "123456"}
    )
    assert resp.status_code == 200
    assert "token" in resp.json()

### 5.3 测试数据管理

测试数据应独立于生产数据，使用独立的测试数据库。

每次测试前准备数据，测试后清理数据。

敏感数据（如密码）应加密存储。

### 5.4 持续集成

接口测试应接入 CI，每次代码提交自动运行。

CI 中运行的用例应是稳定的、快速的、无外部依赖的。

不稳定用例应单独管理，避免影响 CI 通过率。

## 第六章 接口鉴权

### 6.1 常见鉴权方式

**Session 鉴权**：服务端存 session，客户端存 sessionId。

**Token 鉴权**：服务端签发 token，客户端每次请求携带。

**JWT 鉴权**：Token 自包含用户信息，服务端无状态。

**OAuth2**：第三方授权，常用于开放平台。

**API Key**：服务端签发 key，客户端携带，适合机器对机器。

### 6.2 鉴权测试场景

Token 缺失：预期返回 401。

Token 格式错误：预期返回 401。

Token 过期：预期返回 401。

Token 签名错误：预期返回 401。

Token 有效但无权限：预期返回 403。

Token 被撤销：预期返回 401。

### 6.3 JWT 结构

JWT 由三部分组成，用点分隔：

Header.Payload.Signature

Header：算法和类型。

Payload：用户信息、过期时间等。

Signature：签名，防篡改。

## 第七章 接口性能测试

### 7.1 性能指标

响应时间：P50、P95、P99。

吞吐量：QPS、TPS。

并发数：同时处理的请求数。

错误率：失败请求占比。

资源使用：CPU、内存、网络。

### 7.2 性能测试类型

**负载测试**：逐步增加负载，观察系统表现。

**压力测试**：超过系统容量，观察崩溃点。

**稳定性测试**：长时间运行，观察是否泄漏。

**尖峰测试**：瞬间高并发，观察系统响应。

### 7.3 性能测试工具

JMeter：功能全，图形界面。

Locust：Python 编写，代码灵活。

Gatling：Scala 编写，性能高。

wrk：命令行，轻量。

## 第八章 接口安全测试

### 8.1 常见安全问题

SQL 注入：输入恶意 SQL 片段，试图执行非法查询。

XSS：输入恶意脚本，试图在页面执行。

CSRF：伪造请求，操作用户数据。

越权：访问他人资源。

敏感信息泄露：响应中包含密码、身份证等。

暴力破解：大量尝试密码。

### 8.2 安全测试方法

SQL 注入：输入 ' OR '1'='1，观察是否绕过鉴权。

XSS：输入 <script>alert(1)</script>，观察是否弹窗。

越权：用 A 的 token 访问 B 的资源，观察是否成功。

敏感信息：检查响应体，是否有密码、身份证等。

暴力破解：连续错误登录，观察是否锁定。

## 第九章 接口文档

### 9.1 文档规范

接口文档应包含：

接口名称、描述。

请求方法、URL。

请求头。

请求参数（路径、查询、请求体）。

响应示例。

CI 中增加文档检查，确保文档与代码一致。

## 第十章 常见接口设计模式

### 10.1 RESTful 风格

用 HTTP 方法表示操作：

GET：查询。

POST：创建。

PUT：全量更新。

PATCH：部分更新。

DELETE：删除。

URL 用名词表示资源，如 /api/users/123。

### 10.2 RPC 风格

用 URL 表示动作，如 /api/getUser。

常用 POST 方法。

参数在请求体中。

### 10.3 GraphQL

客户端指定需要的字段。

一个接口支持多种查询。

适合复杂前端场景。

### 10.4 幂等性设计

幂等性：同一请求执行多次，结果一致。

实现方式：

唯一索引：数据库唯一约束。

Token 机制：客户端先获取 token，请求时携带。

状态机：只允许合法状态跳转。

### 10.5 限流设计

限流：限制单位时间内的请求数。

实现方式：

计数器：Redis 计数。

令牌桶：固定速率放行。

漏桶：固定速率处理。

滑动窗口：精确控制。

限流返回 429，响应体提示「操作过于频繁」。

### 10.6 熔断降级

熔断：依赖服务异常时，快速失败，避免雪崩。

降级：依赖服务不可用时，返回兜底数据。

实现方式：

Hystrix：Netflix 开源。

Sentinel：阿里开源。

Resilience4j：轻量级。

### 10.7 灰度发布

灰度：新版本先给部分用户使用。

实现方式：

按用户 ID 取模。

按地域。

按设备。

按请求头。

灰度期间监控指标，异常时回滚。

## 第十一章 接口测试常见问题

### Q1：接口返回 500，怎么排查？

A：先看服务端日志，定位异常堆栈。常见原因：空指针、数据库连接失败、依赖服务超时。

### Q2：接口返回慢，怎么排查？

A：用 APM 工具（如 SkyWalking）看调用链，定位慢在哪一步。常见原因：数据库慢查询、依赖服务慢、GC。

### Q3：接口偶发失败，怎么排查？

A：看日志中的错误频率和时间分布。常见原因：并发问题、缓存击穿、网络抖动。

### Q4：接口返回数据结构变了，怎么办？

A：与开发确认变更原因，评估影响范围。更新测试用例，回归相关接口。

### Q5：接口鉴权怎么测？

A：覆盖 Token 缺失、格式错误、过期、签名错误、无权限等场景。

### Q6：接口幂等性怎么测？

A：同一请求提交多次，验证结果一致，数据不重复。

## 第十四章 附则

### 14.1 接口版本管理

URL 中带版本号，如 /api/v1/users。

旧版本保留至少 6 个月。

版本废弃提前 3 个月通知。

### 14.2 接口命名规范

URL 用小写字母和短横线，如 /api/user-profiles。

避免动词，用 HTTP 方法表示操作。

资源名用复数，如 /api/users。

### 14.3 接口返回规范

统一返回结构：
{
  "code": 0,
  "message": "success",
  "data": {...}
}

错误返回：
{
  "code": 40001,
  "message": "用户名不能为空",
  "data": null
}

code 为 0 表示成功，非 0 表示失败。

### 14.4 接口超时规范

客户端超时：建议 10 秒。

服务端超时：建议 30 秒。

超时后必须返回明确错误，不能挂起。

### 14.5 接口日志规范

记录请求 ID、用户 ID、接口路径、请求参数、响应状态、耗时。

敏感字段（密码、身份证）不记录。

日志保留至少 30 天。

## 第十五章 接口测试进阶场景

### 15.1 幂等性测试

幂等性是指同一请求执行多次，结果一致。常见需要幂等的接口：

| 接口 | 幂等要求 |
|---|---|
| 创建订单 | 同一请求 ID 只创建一次 |
| 支付 | 同一订单只支付一次 |
| 退款 | 同一订单只退款一次 |
| 提交表单 | 重复提交不产生重复数据 |

**测试方法**：
1. 同一请求快速提交两次
2. 观察是否只创建一条记录
3. 观察返回结果是否一致

**实现方式**：
- 唯一索引：数据库唯一约束
- Token 机制：客户端先获取 token，请求时携带
- 状态机：只允许合法状态跳转

### 15.2 并发测试

并发测试验证多请求同时到达时的数据一致性。常见并发场景：

**库存扣减**：100 个用户同时抢 10 件商品，验证是否超卖。

**优惠券领取**：100 个用户同时领 1 张券，验证是否超发。

**账户余额**：同一账户并发扣款，验证余额是否正确。

**测试方法**：
1. 用 JMeter 或 Locust 模拟并发
2. 观察数据库最终状态
3. 验证是否有脏数据

### 15.3 超时测试

超时测试验证依赖服务响应慢时的处理。

**场景 1：数据库慢查询**
- 模拟数据库响应 10 秒
- 验证接口是否超时
- 验证是否返回明确错误

**场景 2：第三方服务超时**
- 模拟支付渠道响应慢
- 验证接口是否降级
- 验证是否给用户明确提示

**场景 3：网络抖动**
- 模拟网络延迟
- 验证重试机制
- 验证最终一致性

### 15.4 熔断降级测试

**熔断**：依赖服务异常时，快速失败，避免雪崩。

**降级**：依赖服务不可用时，返回兜底数据。

**测试方法**：
1. 模拟依赖服务连续失败
2. 观察是否触发熔断
3. 观察降级逻辑是否生效
4. 模拟依赖服务恢复
5. 观察是否自动恢复

### 15.5 限流测试

**限流**：限制单位时间内的请求数。

**常见限流策略**：

| 策略 | 说明 |
|---|---|
| 计数器 | 固定时间窗口内计数 |
| 令牌桶 | 固定速率放行 |
| 漏桶 | 固定速率处理 |
| 滑动窗口 | 精确控制 |

**测试方法**：
1. 短时间内发送大量请求
2. 观察是否返回 429
3. 观察响应头是否含 Retry-After
4. 等待限流窗口过后，验证恢复

### 15.6 灰度测试

**灰度**：新版本先给部分用户使用。

**灰度策略**：
- 按用户 ID 取模
- 按地域
- 按设备
- 按请求头

**测试方法**：
1. 灰度用户访问新版本
2. 非灰度用户访问旧版本
3. 验证功能一致性
4. 观察灰度指标
5. 异常时回滚

### 15.7 数据一致性测试

**场景 1：跨表事务**
- 订单表创建成功
- 订单详情表创建失败
- 验证是否回滚

**场景 2：缓存与数据库**
- 修改数据库
- 验证缓存是否更新
- 验证读取是否一致

**场景 3：上下游服务**
- 服务 A 调用服务 B
- 服务 B 失败
- 验证服务 A 是否回滚

### 15.8 接口兼容性测试

**向后兼容**：
- 新增字段不影响老客户端
- 删除字段需评估影响

**测试方法**：
1. 用旧版本客户端调用新版本接口
2. 验证是否正常
3. 用新版本客户端调用旧版本接口
4. 验证是否降级

### 15.9 接口版本管理测试

**版本策略**：
- URL 带版本：/api/v1/users
- Header 带版本：Accept: application/vnd.api.v1+json

**测试方法**：
1. 调用 v1 接口，验证正常
2. 调用 v2 接口，验证正常
3. 调用废弃版本，验证提示升级
4. 验证版本间数据一致性

### 15.10 接口监控与告警测试

**监控指标**：
- QPS
- 响应时间 P50/P95/P99
- 错误率
- 超时率

**告警规则**：
- 错误率 > 1%
- P99 > 1 秒
- QPS 突降 > 50%

**测试方法**：
1. 人为制造错误
2. 验证告警是否触发
3. 验证告警内容是否准确
4. 验证告警渠道是否畅通

## 第十九章 接口测试常见反模式

### 19.1 只测正常场景

只测正常场景，忽略边界和异常，是最常见的反模式。上线后容易出问题。

### 19.2 依赖真实数据

测试用例依赖生产数据，导致不可重复、不稳定。

### 19.3 断言不充分

只断言状态码，不断言响应体，无法发现数据错误。

### 19.4 用例耦合

用例之间有依赖，导致执行顺序敏感。

### 19.5 忽略性能

只测功能，不测性能，上线后接口慢。

### 19.6 忽略安全

不测鉴权、越权、注入，存在安全风险。

### 19.7 文档不同步

接口变更后文档不更新，导致测试遗漏。

### 19.8 缺少监控

上线后无监控，故障发现晚。

### 21.2 常用状态码速查

| 状态码 | 含义 |
|---|---|
| 200 | 成功 |
| 201 | 创建成功 |
| 204 | 成功无内容 |
| 400 | 请求参数错误 |
| 401 | 未授权 |
| 403 | 无权限 |
| 404 | 资源不存在 |
| 405 | 方法不允许 |
| 409 | 资源冲突 |
| 422 | 语义错误 |
| 429 | 请求过频 |
| 500 | 服务器错误 |
| 502 | 网关错误 |
| 503 | 服务不可用 |
| 504 | 网关超时 |

### 21.3 常用断言

- 状态码断言：assert resp.status_code == 200
- 字段存在断言：assert "token" in resp.json()
- 字段值断言：assert resp.json()["code"] == 0
- 响应时间断言：assert resp.elapsed.total_seconds() < 1
- 结构断言：assert isinstance(resp.json()["data"], list)
